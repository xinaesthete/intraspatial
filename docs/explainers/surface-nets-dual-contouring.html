Isosurface extraction · compute pass

From a field of numbers to a mesh

A scalar field — an analytic SDF, or a sampled volume — is just a number at every point. Surface nets and dual contouring turn the surface where that number crosses zero into triangles, one independent cell at a time. That independence is what makes it a natural fit for a GPU compute pass. Here's the whole idea, in two dimensions you can poke at.

The setup

A grid, a sign at every corner

Everything starts with a function f(p) that returns a signed number: negative inside the solid, positive outside, zero exactly on the surface. Two things produce such a field, and the extraction code doesn't care which:

analytic
a signed distance function — a sphere, a box, a smooth-union of them. Cheap to evaluate anywhere; gradients are exact or a few extra taps.
sampled
a volume — a voxel grid, a medical scan, a density field. You read f by fetching (and interpolating) the nearest samples.

Lay a regular grid over the field and evaluate f at every corner. Each corner is now simply inside or outside. Wherever an edge of the grid connects an inside corner to an outside corner, the surface must cross that edge — a sign change. Those bipolar edges are the entire signal; the rest of the grid is empty space we skip.

Primal vs. dual

Where do the vertices go?

Two families answer this differently. Marching cubes is primal: it puts vertices on the grid edges at the crossings, then stitches them per-cell from a 256-entry case table. Surface nets is dual: it puts one vertex inside each cell that straddles the surface, then connects the vertices of neighbouring cells across each shared bipolar edge.

Primal — vertices on edges

Marching squares/cubes. Vertices live where the surface cuts an edge; topology comes from a case table per cell.

Dual — one vertex per cell

Surface nets. Vertices live inside cells; edges are dual to the grid's bipolar edges. Fewer, more uniform quads.

The dual layout is why this family is attractive for us: the mesh is a clean quad grid (uniform valence, easy to relax or subdivide), each cell is independent during vertex placement, and — crucially — the single free vertex per cell is a degree of freedom we can aim. That's the opening dual contouring exploits.

Placing the vertex

The QEF: aiming the vertex at the corner

Naive surface nets place the cell's vertex at the average of its edge crossings — roughly the cell centre. On a smooth surface that's fine. On a hard edge it's a disaster: the average sits in the middle of the cell and the corner gets sanded flat (you just watched it in the demo).

Dual contouring keeps more information at each crossing: not just where the surface cuts the edge, but the gradient — the surface normal — there. This crossing-plus-normal pair is Hermite data. Each crossing then defines a line (in 3D, a plane) the surface is tangent to, and the ideal vertex is the point that lies on all of them at once.

The quadratic error function. With crossings pi and unit normals ni, place the vertex at the x minimising E(x) = Σi ( ni · (x − pi) )2 — the summed squared distance to every tangent plane. Two crossings on two faces of a corner give two planes whose intersection is the corner, so x lands exactly on it. Minimising is a tiny normal-equations solve (ATA x = ATb, a 3×3 system per cell), regularised toward the cell centre so flat or near-parallel crossings stay stable, and clamped to the cell so it can't shoot off.

That's the whole difference between the two toggle states: same grid, same crossings, same connectivity — naive averages, dual solves. Everything else about the algorithm is identical.

On the GPU

Three passes over independent cells

Because each cell classifies and places its vertex without talking to its neighbours, the work maps onto a compute dispatch almost directly. The only genuinely global step is compaction — turning the sparse set of active cells into a packed vertex buffer with stable indices. A common shape:

PASS 01

Classify

One thread per cell (or per corner). Sample f, read off the 8 corner signs, mark the cell active if any edge is bipolar. Count actives.

in: field / SDF out: active mask out: counts
PASS 02

Place & compact

Prefix-sum the mask (or an atomic bump) to give each active cell a slot. Per active cell: find crossings, tap gradients, solve the QEF, write the vertex. Store the cell→slot map.

in: active mask scan / atomics out: vertices out: slot map
PASS 03

Connect

One thread per bipolar edge. Look up the (2 in 2D, 4 in 3D) adjacent cells' slots and emit a quad/triangle fan. Append to an index buffer sized for an indirect draw.

in: slot map out: indices out: draw args
  • Compaction is the real work. A dense grid is mostly empty; you don't want a vertex slot per cell. A parallel prefix-sum over the active mask (or a per-workgroup atomic counter feeding a global offset) packs actives contiguously and hands each one the stable index its neighbours will look up in pass 3.
  • Indexing must be deterministic. Pass 3 references a cell's vertex by the slot pass 2 assigned — the two passes must agree on cell→slot with no race. This determinism is also what lets a re-run reproduce the same buffers (it matters for us: it's how a picking id stays stable).
  • Everything feeds an indirect draw. Vertex and index counts aren't known on the CPU; write them into a draw-args buffer and issue drawIndexedIndirect — the mesh never round-trips through the CPU.
  • 3D adds a case table for connectivity (which edges of a cell are bipolar), but vertex placement stays the same one-QEF-per-cell. Transvoxel / manifold-dual-contouring variants handle LOD seams and non-manifold cells.
Where this lands for us

One extraction pass, several sources

This is the mesh side of the implicit geometry-kind (ADR-0010), and the same pass is how we get geometry from data. The field being contoured is the only thing that changes:

  • Plane-based / CSG. Half-spaces and boxes combined with min/max booleans — the classic constructive solids. Sharp by nature, so dual contouring (not naive surface nets) is the right default; the corners are the whole point.
  • General implicit & smooth-ops. Smooth-union, blends, arbitrary F(x,y,z)=0. Note these aren't always true distance fields — a non-Lipschitz F needs care at the crossing solve (or interval arithmetic, the way the prior-art CSG field did) rather than a naive lerp.
  • Data-derived. The isosurface of a sampled volume — a spatial image, a density. Identical pass; f is a texture fetch and the gradient is a finite difference of samples.
Provenance rides along (ADR-0012). When the field is a primitive tree, pass 2 already knows which primitive was the argmin of the min/max at each vertex — write that id into the vertex, and a picked triangle resolves back to the CSG leaf that made it. Pair it with the depth the render seam always produces (for world-position reconstruction — orbit-pivot under the cursor) and picking-id + depth are co-produced outputs. For a data-derived surface there's no primitive tree, so the token becomes a field-space address instead — same resolver, different token.

On watertight mesh booleans specifically (exact predicates, guaranteed-manifold output for export): that's the case for buying Manifold (C++→wasm) rather than writing it — and it's why the Rust route isn't worth opening here.

Caveats worth remembering: the QEF can be ill-conditioned on near-flat cells (regularise + clamp); dual meshes can be non-manifold where a cell holds more than one surface sheet (needs vertex splitting); and self-intersections happen on thin features below the grid size. None of these are visible in the 2D toy above — they're the reason the 3D production versions are longer.
